绩效工作台 v0.1 — 公司自托管试点
交付日期：2026-11-10

根据“设计绩效系统方案”对话的最后决定实施：自建网页应用、自有数据库及附件存储、飞书工作台入口。推荐先以 2—3 个真实协作部门试点，再推广到 160 多名员工、43 个部门。

一、当前已实现
1. 员工、直属上级、HRBP、逐项验收人、绩效管理员的操作页面。
2. 月份开启；主管确认目标方案；员工本人确认；目标变更原因和历史版本。
3. 权重合计 100% 校验；HRBP 提前分派、批量分派及改派原因。
4. 成果说明、附件上传下载、验收通过、退回补充和重新提交。
5. 服务端人员/记录/状态权限校验；并发版本冲突时拒绝覆盖。
6. 公司工作日历覆盖；次月第 5 个工作日计算；到期仍缺评的记录保留原状态。
7. 经管理员录入批准依据后的模块评分配置；指定主体百分制加权；有效 0 分与未评区分。
8. 红线归零；最终分封顶 100；未完成流程及未配置规则时拒绝发布。
9. 发布、归档固定快照；Excel 五个工作表导出；中文 PDF 导出。
10. 飞书 OAuth 登录代码、8 小时服务端会话、账号预导入授权。
11. 单机 SQLite WAL 数据库；本地附件；备份命令；可选每分钟检查并开启当月考核。

二、尚需你们完成的接入
公司服务器和实际域名尚未连接；飞书企业自建应用尚未创建，登录未与真实租户联调；真实组织名单尚未导入。在线私有试点仅使用虚构数据和体验身份切换，公司生产版不启用体验身份切换。

评分主体、最终模块权重、双门槛、特殊加分/双审批仍待制度确认。本版没有替你们决定这些口径。默认不配置任何正式评分规则；跨部门验收不自动转成数字分。若最终制度要求跨部门数字评分、加分、分档或双门槛，需在批准后扩展规则引擎，再开放真实结果发布。

三、最短本地试用（无需安装第三方运行依赖）
安装 Node.js 24 LTS 或以上版本。在本目录执行：
Windows PowerShell：
  $env:DEMO_MODE='true'
  node local/server.mjs
Linux/macOS：
  DEMO_MODE=true node local/server.mjs
打开 http://127.0.0.1:4310 。演示仅监听本机回环地址。
交付包已包含构建好的 selfhost/public，无需 npm install。

四、飞书应用创建
详见同目录“飞书应用创建说明.txt”。用户无需把 App Secret 发到聊天中。由 IT 在公司服务器 .env 文件配置。

五、Linux / Windows 直接部署
1. 解压到应用专用目录，安装 Node.js 24+。
2. 将 .env.example 复制为 .env，填写 APP_BASE_URL（HTTPS 根域名、末尾不要斜杠）、FEISHU_APP_ID、FEISHU_APP_SECRET，保持 DEMO_MODE=false。
3. 准备 people.json，字段见 people.example.json；由管理员绑定同一自建应用的员工 Open ID。
4. 执行：node --env-file=.env local/admin.mjs import people.json
5. 执行：node --env-file=.env local/server.mjs
6. 使用 systemd 或 Windows 服务管理器保持进程运行；反向代理 HTTPS 到 127.0.0.1:4310。Nginx 示例见 nginx.example.conf。
7. 企业自建应用发布给 2—3 个试点部门，测试真实账号后推广。
本机 demo 与 company 数据使用不同工作区；不要把虚构人员导入生产名单。

六、Docker 部署（公司已有 Docker 时）
1. 按第五部分准备 .env 和 people.json，执行 mkdir -p data，并将 data 目录属主设为 UID 1000（容器 node 用户）。
2. docker compose build
3. docker compose run --rm performance node local/admin.mjs import /data/people.json
   第三步前将名单临时放到 data/people.json；导入后从该目录移走名单。
4. docker compose up -d
5. 配置 Nginx HTTPS 和飞书回调，再验证 /health 与人员登录。
容器只把 4310 映射到宿主机回环地址，data 目录须持久化。

七、备份及恢复
直接部署备份：
  node --env-file=.env local/admin.mjs backup /另一路径/绩效备份-日期
Docker 备份（先建立容器内可写备份挂载目录）：
  建议用宿主机 Node 24 执行同一命令并将 DATA_DIR 指向持久化 data；或为备份目录添加独立挂载后在容器内执行。
备份包含一致性 SQLite 快照和只新增的附件目录。备份命令已本地验证。
恢复：停止应用；将当前 data 整体移到保留目录；将备份的 performance.sqlite 和 attachments 恢复到新的 data；恢复目录权限；启动应用。恢复旧备份会使之后的会话、记录和文件不可见，先保留当前数据。不得混用旧数据库和新的 WAL/SHM 文件。
安排现有 IT 定时备份，保留异机副本，定期用隔离目录演练恢复。密钥配置由现有 IT 秘密管理方式备份。

八、试点验收顺序
林悦确认目标 → 陈嘉 HRBP 分派未分派任务给许航 → 林悦提交成果 → 许航退回 → 林悦补齐重提 → 许航通过 → 周宁处理内部任务并评分（仅测试规则） → 陈嘉核对日历并发布、归档 → 导出 Excel / PDF。
用真实账号额外验证：员工互不可见，验收人只见所分任务，非主管不能代评分，归档不随人员调岗改变。

九、开发和架构说明
托管私有试点：Vinext/React + D1 + R2，ChatGPT 身份隔离体验工作区。此入口供你本人检查流程；公司员工正式入口部署到你们自己的服务器。
自托管：React 静态前端 + Node 原生 HTTP + Node 内置 SQLite + 本地附件。无需 Redis，无额外 SaaS 订阅。
业务引擎在 lib/performance.mjs，两种部署共用。试点采用单条工作区 JSON 快照与数据库 revision 原子更新；部署为单实例。这是小范围试点实现，未做 160 人并发负载测试；全员推广前应做容量测试，并按实际负载将快照拆分为人员、周期、考核、任务、评价和审计等独立表。不要声称此版已完成生产容量验证。
流程审计随业务原子保存，属于应用可追溯日志；具备服务器写权限的管理员仍可更改数据库，不属于防篡改电子签章或第三方法律存证。
附件限制：每任务 10 个，每文件 10 MB，权限下载以附件方式返回。本版不扫描附件病毒，沿用公司既有终端及存储安全措施。
PDF 为中文固定版式，使用 PDF 标准中文字体；Excel 为真实 OOXML，字符串按文本保存。

重建前端：安装开发依赖后 node local/build.mjs。
测试：node --test tests/workflow.test.mjs。
在线试点重新部署：按 Sites 已保存项目 ID 继续构建和发布，勿创建重复项目。
